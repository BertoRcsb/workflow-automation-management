1. Sumario executivo

Hoje o workflow-automation-management e um conjunto de instrucoes (skills em Markdown) que so roda dentro do Claude Code, com os MCPs Atlassian e Notion ligados por OAuth manual. Ele documenta releases no Notion e prepara a sincronizacao de branches acionando o sync-repos-from-master.

Este documento define um gemeo autonomo: o mesmo papel "Optimus Prime", porem em codigo real, rodando como pipeline sem o Claude no meio. O sistema atual e preservado (fica como a versao assistida por IA); criamos um repositorio novo, separado, espelhando a arquitetura limpa ja provada no sync-repos-from-master.

O que muda

MotorClaude Code lendo skillsCodigo Python (Clean Architecture)

Premissas travadas

  • Repositorio novo, Python 3.14 + Poetry, espelhando o sync-repos-from-master.
  • Execucao por CLI + agendador (cron/systemd), com comando unico no estilo do Sync.
  • Card ambiguo (heuristica so-banco nao fecha, ou repositorio diferente da PR) e excluido e reportado - 100% deterministico, sem chamada de IA em runtime.
  • Gates humanos por comando separado: executar vai so ate o make dry-run do Passo 1 e emite a mensagem Optimus Prime retornando com o resultado = Confira; make run, master e triggers ficam guardados sob OK do Ronan.
  • "Assignee de banco" deixa de ser conhecimento tacito e vira um cadastro db_owners na configuracao.

2. Visao geral do sistema

O "Optimus Prime" em codigo e o cerebro; os bracos continuam sendo Jira (leitura), Notion (escrita) e o sync-repos-from-master (deploy). O que antes exigia o Claude operando MCPs agora sao chamadas REST diretas e a orquestracao dos make do sync-tool.

D1 - Visao geral: disparo (agendador/operador) -> Optimus Prime -> Jira / Notion / sync-tool.

3. Arquitetura em camadas

Clean/Hexagonal identica a referencia: direcao de dependencia interfaces → application → domain ← infra. O domain define contratos (ABCs) e regras puras sem I/O; o infra implementa os contratos (adapters REST); o application orquestra recebendo os contratos por injecao de dependencia.

D2 - Camadas e modulos do pacote optimus_prime.

Padroes reusados do sync-repos-from-master: CLI com argparse e roteamento por primeiro argumento; @dataclass(slots=True) + Literal para status; BaseAdapter.safe_call() que converte falhas conhecidas em resultado normalizado sem quebrar o lote; adapters com transport injetavel (testaveis sem rede); saida chave=valor + exit code.

4. Fluxo da esteira

No executar de um board, a esteira roda de forma autonoma da coleta ate o make dry-run do Passo 1, encerrando na mensagem unica Confira. A unica excecao que interrompe e um erro; o card ambiguo nao pausa - e excluido e reportado.

D3 - Sequencia dos passos 1 a 7; para no dry-run + Confira; make run e deploy sob OK do Ronan.

5. Regras de negocio

Toda a decisao de elegibilidade e dependencia vira codigo deterministico e testavel (camada domain/rules.py). A regra v2 (aprovar se tem PR+repositorio, ou se e legitimamente so-banco), a heuristica so-banco, e as regras de dependencia D1 (epico incompleto) e D2 (PR compartilhada parcial) sao aplicadas em sequencia; o card ambiguo e excluido e reportado.

D4 - Elegibilidade v2 + so-banco + D1/D2 + tratamento deterministico do card ambiguo.

6. Governanca e seguranca

A fronteira de autonomia e clara: tudo ate o make dry-run do Passo 1 roda sozinho; todo make run (Passo 1 e 2), o merge, o master e as triggers (Passo 3) exigem OK explicito do Ronan. O auto_merge permanece false; o make run sempre com target explicito, nunca direto para a master.

D5 - O que e autonomo vs. o que fica sob OK do Ronan; invariantes inquebraveis.

7. Roadmap de construcao

A construcao e dividida em sete Passos sequenciais. O Passo 4 entrega o primeiro valor real (le e valida cards sem escrever nada) e o Passo 6 completa a esteira autonoma.

D6 - Sequencia dos Passos 1 a 7 e os dois marcos de valor.

Passo 1 - Scaffold do repositorio

Objetivo

Criar o repositorio novo com o esqueleto de Clean Architecture, ferramentas de qualidade e configuracao, espelhando o sync-repos-from-master. Nenhuma regra ainda; so a fundacao.

Subtarefas

  • Criar o repo workflow-automation-pipeline (nome ajustavel) e o pacote src/optimus_prime.
  • pyproject.toml (Poetry, Python 3.14): pyyaml; dev: pytest, pytest-cov, ruff, black.
  • Layout de pastas: interfaces/ application/ domain/ infra/ shared/ tests/.
  • Makefile: alvos setup lint format test verificar executar executar-todos promote-passo1 promote-master triggers.
  • .env.example, pipeline.yaml.example, deploy_requirements.yaml.
  • Hook .githooks/pre-commit (deps-check + test com cobertura minima 80%); ruff+black configurados.

Entregaveis

Repo instalavel (make setup), make test verde vazio, lint/format limpos.

Criterio de conclusao: make setup e make test rodam sem erro; estrutura de camadas criada; hook de pre-commit ativo.

Dependencias: nenhuma.

Passo 2 - Dominio puro (regras)

Objetivo

Codificar todo o "cerebro de decisao" como funcoes puras e modelos, sem nenhum I/O - a parte mais critica e a que ganha os testes mais fortes.

Subtarefas

  • domain/models.py: Card, Links (repositories e pull_requests como listas), DeployFields, Epic, ValidationResult, ReleaseDoc, ExecutionSummary.
  • domain/boards.py: registro dos 3 boards com a JQL exata (incidentes 1o).
  • domain/rules.py: eligibility_v2, so_banco_legitimo, is_ambiguous, d1_epico_incompleto, d2_pr_parcial, next_version.
  • Tratar "N/A" e "Apenas PROC" como vazio; deduplicar links.
  • Testes dos casos-modelo (ver Apendice B): PB-5778, PB-5599, PB-5159, PB-5768, D1, D2, ambiguo.

Entregaveis

Modulo domain completo e coberto por testes; zero dependencia de rede.

Criterio de conclusao: todos os casos-modelo passam; cobertura do domain proxima de 100%.

Dependencias: Passo 1.

Passo 3 - Adapter Jira + parsers

Objetivo

Falar com o Jira por REST direto (o que hoje o MCP faz), normalizando cada card no contrato do dominio, com atencao ao multi-link e a PR-por-referencia.

Subtarefas

  • infra/jira/jira_client.py: urllib + transport injetavel; auth Basic (email:token); search por JQL e get issue pedindo so os campos necessarios.
  • infra/jira/field_parsers.py: extrair TODOS os URLs de customfield_12399/12400; deduplicar; resolver "Pr no card PB-XXXX" herdando PR/repo.
  • Ler o parent (epico) e, para D1, os filhos do epico e seus status.
  • Implementar a ABC IssueSource do dominio.
  • Testes com transport fake (respostas Jira gravadas) - sem rede.

Entregaveis

Adapter Jira testado que devolve Cards normalizados a partir de respostas reais gravadas.

Criterio de conclusao: dado um payload Jira de exemplo, o adapter produz o card normalizado correto (multi-link e PR-por-referencia inclusos).

Dependencias: Passo 2.

Passo 4 - Coletor + Validador + CLI verificar

Objetivo

Primeiro marco de valor real: ler e validar cards de um board de verdade, sem escrever nada.

Subtarefas

  • application/collector.py: monta a JQL do board, chama o IssueSource, normaliza.
  • application/validator.py: aplica v2 + so-banco + D1/D2; separa aprovados/reprovados/excluidos/ambiguos.
  • application/reporter.py: relatorio chave=valor + ExecutionSummary em execucoes/.
  • interfaces/cli.py: comando verificar BOARD=<board> (dry, so leitura).

Entregaveis

make verificar BOARD=incidentes lista cards normalizados e a separacao de decisao, contra o Jira real, sem tocar em Notion nem no YAML.

Criterio de conclusao: o verificar roda fim-a-fim de leitura e o resultado bate com a conferencia manual de um pacote conhecido.

Dependencias: Passo 3.

Passo 5 - Adapter Notion + Montador

Objetivo

Escrever/atualizar a pagina da versao no Notion no molde padrao, de forma idempotente.

Subtarefas

  • infra/notion/notion_client.py: query da ultima versao (data_source), criar/atualizar pagina; escrita assincrona com poll + re-fetch de verificacao.
  • Implementar a ABC DocStore.
  • application/assembler.py: versao-alvo X.(Y+1).0; tabela (Item, Pull Requests, Banco, Infra, Merge); blocos fixos (Testes, Ambientes, Repositorios para Deploy, Participantes); todos os links por card.
  • Idempotencia: se a pagina da versao existe, atualiza (nao duplica).
  • Testes do montador com DocStore fake; testes do adapter com transport fake.

Entregaveis

Pagina montada corretamente na base de teste do Notion (1.111.0 (teste)).

Risco: a tabela do Notion via API sao blocos - e a integracao mais complexa. Ganha um modulo de template dedicado e testes proprios.

Dependencias: Passo 4.

Passo 6 - Sync bridge + Orquestrador + CLI executar

Objetivo

Fechar a esteira autonoma: governar o repos.yaml, rodar o make dry-run do Passo 1 e emitir a mensagem Confira.

Subtarefas

  • infra/sync/make_sync_runner.py: editar o repos.yaml em $SYNC_REPO_PATH (ativar so os repos de "Repositorios para Deploy", triggers comentados, resto comentado, repo faltando -> para e reporta); subprocess do make dry-run; parsear chave=valor + exit code.
  • Implementar a ABC SyncRunner.
  • application/orchestrator.py: encadeia versao-alvo -> coletor -> validador -> montador -> sync bridge (dry-run) -> relatorio.
  • interfaces/cli.py: executar BOARD=<board> e executar-todos; emite a linha Confira + artefatos; grava execucoes/.
  • Erros -> post-mortem erros/AAAA-MM-DD-slug.md.

Entregaveis

make executar BOARD=incidentes vai da coleta ao dry-run e encerra na mensagem Confira, sem abrir nenhum PR.

Criterio de conclusao: esteira completa autonoma ate o dry-run; execucoes/ gravado; nenhum make run disparado sozinho.

Dependencias: Passo 5.

Passo 7 - Promocao guardada + agendador + docs

Objetivo

Entregar os comandos de promocao sob OK do Ronan, o agendamento e a documentacao do novo repo.

Subtarefas

  • make promote-passo1 VERSAO=... (make run que abre os PRs pre-prod), promote-master (Passo 2), triggers (Passo 3) - todos guardados.
  • Garantir auto_merge=false e target explicito sempre.
  • Unit systemd (ou cron) chamando make executar-todos no horario definido.
  • README + spec do novo repo (estilo do sync-tool); opcional: nota no repo atual apontando para o pipeline.

Entregaveis

Promocao funcional sob comando; agendamento ativo; documentacao publicada.

Criterio de conclusao: promote-passo1 abre os PRs (auto_merge=false); o agendador dispara o executar-todos; docs completas.

Dependencias: Passo 6.

Riscos e Definition of Done

Riscos

  • Tabela do Notion via API (blocos + escrita assincrona) e a integracao mais complexa - mitigada por modulo de template dedicado, uso da base de teste primeiro e re-fetch de verificacao.
  • Grafia exata das branches (prerelease/teste_regressivo/master) a confirmar antes do run real.
  • Campos sem fonte deterministica (Acao de Infra inexistente, Merge vazio, nome do proc) - ficam em branco, nunca inventados.
  • Cadastro db_owners precisa ser mantido atualizado (quem e responsavel de banco).

Definition of Done do projeto

  • make executar BOARD=<board> roda sem Claude, da coleta ao dry-run, e emite Confira.
  • Regras (v2, so-banco, D1/D2, ambiguo) cobertas por testes; cobertura minima 80%.
  • Notion montado corretamente e idempotente; repos.yaml governado a partir da doc.
  • Promocao (make run/master/triggers) so sob OK do Ronan; auto_merge=false.
  • Agendador ativo; documentacao publicada; repo atual preservado.
